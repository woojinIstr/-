# 다음한끼 통합 실행본 v0.3.5

**v0.3~v0.3.4 사용자는 기존 서버를 종료하고 새 폴더에 압축을 푼 뒤, 기존 `backend/.env`를 복사하고 `START_WINDOWS.cmd`를 실행하세요. 003까지 적용한 Supabase 프로젝트는 추가 SQL이 필요 없습니다.** 로컬 시연 데이터를 옮길 때는 서버를 종료한 상태에서 기존 `SQLITE_PATH`의 DB 파일도 같은 위치로 복사하세요.

## v0.3.5에서 확인할 기능

- 변경 이력 → 조리·사용·폐기 기록의 **기록 되돌리기** → 복원 수량·식사 상태·장보기 변화를 확인 → 확인 및 저장.
- 실제 차감한 구매분으로 수량을 돌려놓습니다. 조리한 식사는 예정으로 돌아가며, 실제 사용량을 수정해 다시 조리할 수 있습니다.
- 같은 기록을 두 번 복원하지 않습니다. 이후 같은 구매분을 수정·사용·폐기·숨김 처리했다면 자동 복원을 막고 이유를 표시합니다. 연속 사용 기록은 최신 기록부터 되돌릴 수 있습니다.
- 다른 구매분이나 장보기 등 별도 작업은 유지됩니다. 중간에 한 구매분만 충돌해도 전체 복원이 취소됩니다.
- 이 버전부터 남긴 구조화된 기록만 자동 복원합니다. 이전 기록의 수량은 추측하지 않습니다. 복원해도 구매일·소비기한은 바뀌지 않습니다.
- `CHECK_SIGNUP_WINDOWS.cmd`: 기존 .env의 공개 키로 회원가입 허용·이메일 로그인·인증 여부를 읽어 확인합니다. 계정 생성이나 설정 변경은 하지 않습니다.
- 실제 프로젝트에서 확인한 설정과 A·D의 후속 작업은 [회원가입 설정 확인](backend/docs/signup-readiness.md)을 참고하세요. 회원가입·비밀번호 복구 화면은 아직 포함하지 않습니다.

## v0.3.4에서 확인할 기능

- 로그인 전 샘플 냉장고 체험. 예시 재료를 선택하고 메뉴를 비교합니다. 샘플의 변경 내용은 브라우저 메모리에서만 사용합니다.
- 홈의 한 끼 고르기와 재료 하나 등록하기. 빈 식사 칸에서 날짜·끼니를 지정해 메뉴를 고릅니다.
- 메뉴 찾기에서 식사 날짜·끼니·인분을 먼저 확인하고 식사에 추가를 누르면 바로 저장됩니다. 메뉴 화면으로 새로 들어갈 때는 오늘 날짜를 표시합니다.
- 장보기의 구매 완료에서 실제 수량을 입력하고 구매 완료 및 재고 반영을 누르면 한 번에 저장합니다. 새 입고는 장보기 항목의 `received_lot_id`로 연결돼 같은 항목의 중복 입고를 막습니다.
- 예전 버전에서 체크만 한 항목은 이전 구매 체크·재고 반영 확인 필요로 표시합니다. 이미 재고에 반영한 것을 확인했다면 목록에서 빼기를 사용할 수 있습니다.
- 재고 추가·메뉴 저장·식사 저장은 바로 저장하며 변경 미리보기를 선택할 수도 있습니다. 조리·사용·폐기·재고 정정·식사 외식·취소 등은 변경 확인을 거칩니다.
- 모바일 하단 냉장고·오늘 식사·장보기 이동, 확대된 메뉴 버튼, 날짜별 예정 식사 수, 세로 포장 입력.
- 예정 식사가 없을 때와 재료가 충분할 때 장보기 안내를 구분합니다.

## v0.3.3에서 추가한 기능

- 장보기에 적은 품목과 수량이 구매 등록창에 이어집니다. 등록하지 않은 품목은 그 이름으로 새 재료를 만들거나 기존 재료를 직접 고를 수 있습니다. 새 재료와 재고, 장보기 체크를 한 번에 저장합니다.
- 두부 2모는 개수 기준 2개로 기록할 수 있습니다. 달걀 2판은 판당 개수를 입력하고, 무게 기준 양파를 봉지로 구입하면 봉지당 무게를 확인합니다. 자동 부족량에서 들어오면 부족한 수량이 초깃값이며 실제 구입량으로 수정할 수 있습니다.
- 구매일·보관 위치·제품 메모는 상세 정보에서 수정합니다. 휴대폰에서도 등록 버튼이 입력창 하단에 표시됩니다.
- 미리보기에서 입력 수정으로 돌아갈 수 있습니다. 다른 창에서 자료가 바뀌면 입력값을 유지하고 최신 내용을 다시 불러옵니다. 변경 확인에는 실제 바뀌는 재고 및 장보기 수량을 표시합니다.
- 홈 요약을 눌러 목록으로 이동합니다. 메뉴 찾기는 1인분에 더 필요한 재료와 수량을 보여줍니다. 결과가 비었을 때는 적용할 수 있는 조리 시간이나 제외 조건을 제안합니다.
- 외식을 저장한 뒤 다음 집밥 고르기로 후속 예정 식사를 바꾸거나 새 식사를 등록할 수 있습니다. 모바일 주간 보기에서는 날짜를 고른 뒤 해당 날짜의 세 끼를 확인합니다.

프론트와 백엔드를 함께 실행하는 개발·시연용 통합본입니다. 외부 식품 검색 DB나 AI API 없이 직접 등록한 재료·메뉴와 확인된 단위로 계산합니다.

## 기존 사용자: 처음 한 번만 준비

1. ZIP을 **새 폴더에** 압축 해제합니다. 이전 작업 폴더는 백업으로 보관합니다.
2. 기존 FastAPI와 프론트 실행 창에서 각각 Ctrl+C로 종료합니다.
3. 기존 backend/.env를 이 폴더의 backend/.env로 복사합니다. APP_MODE=supabase와 기존 URL·Publishable key를 유지합니다.
4. 이미 003까지 적용한 기존 사용자는 **SQL을 다시 실행하지 않습니다.** v0.2에서 처음 전환할 때만 backend/migrations/003_integrated_workspace.sql을 실행합니다. 새 Supabase 프로젝트라면 001 → 002 → 003 순서로 적용합니다.
5. Python 3.11 이상이 설치되어 있는지 확인합니다. 이 ZIP에는 빌드된 화면이 포함되어 있어 **그대로 실행할 때는 Node.js가 없어도 됩니다.** 프론트 소스를 수정해 다시 빌드할 때는 Node.js 22 이상이 필요합니다.
6. 최상위 **START_WINDOWS.cmd**를 더블클릭합니다. 처음에는 Python 라이브러리 설치 때문에 시간이 걸립니다. 이후에는 설치 결과를 재사용합니다.
7. 자동으로 열리는 **http://127.0.0.1:8000**에서 기존 테스트 계정으로 로그인합니다. 실행 창은 켜 둡니다.

프론트 .env는 만들 필요가 없습니다. 백엔드 .env를 기준으로 같은 주소에서 화면과 API가 작동합니다.
이전의 http://localhost:5173 주소는 이 통합본의 기본 실행 주소가 아닙니다.
.env를 미리 복사하지 않으면 실행 프로그램에서 기존 .env 파일 경로를 입력하거나 새 설정을 입력할 수 있습니다.

SQL을 실행하지 않고 내 컴퓨터에서 먼저 시연하려면: 새 폴더의 backend/.env에 APP_MODE=local, APP_ENV=development를 설정합니다. 이 모드는 인증 없는 로컬 시연용이며 다른 사람에게 공개하면 안 됩니다. Supabase 데이터와 별개입니다.

## 인증 최적화와 시간 측정

AUTH_VERIFICATION을 따로 설정하지 않으면 auto입니다. ES256·RS256·EdDSA 공개키 검증이 가능한 프로젝트는 공개키를 5분 동안 재사용하고 토큰은 매 요청 검증합니다. HS256과 공개키 확인이 어려운 경우에는 기존 Supabase 사용자 확인을 유지합니다. 서명 키나 Supabase 프로젝트 설정을 자동 변경하지 않습니다. 매 요청 사용자 최신 상태 확인이 필요한 운영 정책은 AUTH_VERIFICATION=remote로 설정합니다.

정확한 시간은 http://127.0.0.1:8000/?debug=performance 에서 로그인한 뒤 화면 아래 ‘개발용 요청 성능’에서 확인할 수 있습니다. 일반 주소에는 이 표가 나타나지 않습니다. 외부 요청 수·서버 시간·인증 방식만 기록하며 토큰·이메일·입력 내용은 기록하지 않습니다. 자세한 내용은 PERFORMANCE_UPDATE.md를 참고하세요.

## 포함한 기능

- 재료 종류 직접 추가: g / mL / 개수 기준.
- 구매분 등록: 포장 단위·개수·총중량·부피로 입력. kg→g, L→mL 환산.
- 제품 정보 재사용: 이름, 포장당 내용량, 포장 단위, 추정 여부 저장.
- 구매일·소비기한·개봉일과 보관 위치 관리.
- 같은 재료의 총량과 구매분별 잔량 표시. 검색·위치 필터·소비기한순 정렬.
- 소진·숨긴 재고는 기본 목록에서 제외. 숨김은 복원 가능.
- 실제 사용·폐기 수량 기록, 재고 정정, 변경 이력.
- 메뉴 추가·수정·보관·복원, 기준 인분과 필요한 재료·조리 방법 저장.
- 식사 등록·수정·외식·취소·예정 복원.
- 일간·주간 보기, 연속 등록(최대 31일), 다음 날들로 복사.
- 조리 완료 시 실제 사용량 조정. 소비기한이 가까운 구매분부터 차감.
- 부족하면 어떤 재료도 차감하지 않는 원자적 저장. 같은 식사는 중복 조리 불가.
- 오늘 이후 예정 식사의 부족량 계산. 동일 재고 중복 사용 방지, 식사 날짜 전에 소비기한이 지난 재고 제외.
- 수동 장보기와 구매 완료. 실제 입고 수량과 장보기 항목의 재고 반영 상태를 함께 저장.
- 등록·메뉴·식사 저장은 바로 저장할 수 있습니다. 조리·폐기 등 재고를 차감하는 작업과 정정에는 변경 확인을 제공합니다.
- 메뉴 찾기: 시간·제외 재료·우선 재료 및 재료별 충족률 기반 **규칙 검색**. 실제 AI 추천은 미연동.
- 이 탭에서 새로고침 시 로그인 유지(선택), 로그아웃 시 세션 제거.

## 모든 식재료에 적용되는 입력 예시

| 재료 기준 | 구입 수량 | 포장 1단위당 내용량 | 저장 결과 |
|---|---:|---:|---:|
| 닭가슴살, g | 10팩 | 100g | 1,000g, 10팩 |
| 우유, mL | 2병 | 900mL | 1,800mL, 2병 |
| 달걀, 개수 | 2판 | 30개 | 60개, 2판 |
| 쌀, g | 2포 | 10kg | 20,000g, 2포 |

식재료 추가 → 재료 선택 → 입력 단위를 ‘포장 단위’로 선택 → 구입 수량과 1단위당 내용량 입력.
제품 정보 저장에 체크하면 다음 구매 때 ‘저장한 제품’에서 선택할 수 있습니다.
달걀 10개라면 포장 환산 없이 ‘개’ 단위로 10을 입력해도 됩니다.

무게를 모르는 양파는 개수 기준 재료로 관리하거나, 사용자가 확인한 개당 중량을 지정합니다. 추정값이면 ‘추정 내용량’에 체크합니다.
같은 이름의 g 기준 재료가 이미 있으면 ‘양파(개수)’처럼 구분합니다. 개수 재고로 g 기준 레시피를 자동 충족시키지 않습니다.
질량(g)·부피(mL)·개수는 확인된 별도 정보 없이 서로 환산하지 않습니다.

## 권장 확인 순서

1. 기존 재고·메뉴·식사가 보이는지 확인합니다.
2. 닭가슴살 10팩 × 100g을 등록해 1,000g과 10팩 표시를 확인합니다.
3. 다른 재료에서도 포장 환산이 되는지 확인합니다.
4. 새 메뉴를 추가하고 식사로 등록합니다. 반복 일수와 주간 보기를 확인합니다.
5. 조리 완료를 열어 실제 사용량을 확인하고 저장합니다. 잔량·식사 상태·이력이 함께 바뀌는지 확인합니다.
6. 부족한 재료가 있는 조리를 시도해 전체가 거절되는지 확인합니다.
7. 외식·취소 및 예정 복원 시 재고는 그대로이고 부족량만 다시 계산되는지 확인합니다.
8. 사용·폐기로 일부 수량을 기록하고, 숨김 후 필터에서 복원합니다.
9. 장보기 구매 완료 후 재고 추가와 재고 반영 완료 표시를 확인합니다.
10. 새로고침 후 저장·로그인이 유지되는지 확인하고, 두 번째 계정에는 첫 번째 계정의 자료가 나타나지 않는지 확인합니다.

## 기존 v0.2와 데이터 관계 — 꼭 읽기

v0.2의 공통 재료·메뉴 및 로그인한 사용자의 재고·식사를 **v0.3 첫 접속 때 한 번 복사**합니다. 기존 테이블과 파일은 삭제하지 않습니다.
이후 통합본은 `/v3/*` API와 `nextmeal_workspaces`를 사용합니다. 예전 v0.2 화면이나 `/inventory`, `/meals` 등 예전 API의 변경 사항은 양방향 동기화하지 않습니다.
따라서 전환 후에는 **이 통합본 화면과 /v3 API를 기준으로 작업**하고, 이전 실행본과 번갈아 편집하지 마세요.
백업으로 남겨둔 이전 폴더를 실행한다고 v0.3의 변경 내용이 자동으로 이전 버전으로 돌아가지는 않습니다.
처음 복사한 기존 재고의 구매일·소비기한은 임의로 채우지 않고 ‘미입력’으로 표시합니다. 실제 날짜를 아는 경우 정정할 수 있습니다.

메뉴 수정은 이미 등록된 식사의 재료량을 바꾸지 않습니다. 식사는 등록 당시 메뉴 사본을 보관합니다. 새 메뉴 구성을 적용하려면 기존 식사를 취소하고 새로 등록하세요.
v0.3.5부터 새로 남긴 조리·사용·폐기는 변경 이력에서 되돌릴 수 있습니다. 이후 같은 재고가 바뀌면 복원을 막습니다. 연속 사용 기록은 최신 기록부터 되돌리세요. 정정·숨김 등으로 충돌했거나 이전 버전 기록이라면 실제 재고를 확인한 뒤 구매분의 ‘정정’을 사용하세요. 외식·취소는 재고 변경 없이 ‘예정으로 복원’할 수 있습니다.

## 오류 대응

- 8000 포트 사용 중: 기존 백엔드 실행 창에서 Ctrl+C로 종료하세요. 프로그램이 기존 프로세스를 강제로 종료하지 않습니다.
- 503/초기 데이터를 불러오지 못함: Supabase 설정, 001·002·003 적용 여부와 네트워크를 확인하세요.
- 401: 같은 프로젝트의 계정인지 확인하고 다시 로그인하세요.
- 다른 창의 변경으로 409가 나오면 ‘입력 유지하고 새로고침’ 또는 ‘최신 내용 불러오기’를 누르세요. 유지된 입력값과 새 미리보기를 확인한 뒤 저장하세요.
- 시간 초과·네트워크 오류: 저장 확인창을 유지하고 ‘같은 요청으로 재확인’을 누르세요. 같은 요청 ID로 중복 저장을 방지합니다. 결과를 확인하지 않고 새 등록을 반복하지 마세요.
- 단위 오류: 선택한 재료가 g/mL/개수 중 어떤 기준인지 확인하세요.
- 브라우저 새로고침 로그인 유지: 같은 탭에서 유지됩니다. 탭을 닫거나 로그아웃하면 다시 로그인해야 합니다. 브라우저의 탭 복구 동작에 따라 세션이 복구될 수 있으므로 공용 컴퓨터에서는 로그아웃하세요.

## 팀 공유와 현재 범위

backend/는 B, frontend/는 A·D가 검토 후 팀에서 정한 브랜치에 반영합니다. 백엔드는 B, 통합·연동 변경은 D 브랜치 기준으로 공유합니다.
통합 실행본은 한 ZIP으로 전달하지만 소스는 담당별 폴더로 나뉘어 있습니다.
.env, .venv, node_modules, dist, *.db, .setup은 GitHub에 올리지 않습니다.
실제 AI 추천(C), 외부 식품 검색·바코드·사진 인식은 포함하지 않았습니다.
계정 회원가입·비밀번호 재설정·공개 배포 설정도 별도 작업입니다. 이 실행본은 localhost에서 동작합니다.

시연 규모에서는 한 계정의 작업 상태를 JSON 문서로 저장하고 revision을 비교해 한 번에 교체합니다. 메뉴·재고·식사·부족량이 서로 어긋나지 않도록 같은 변경 단위로 저장합니다.
사용자별 RLS와 인증 RPC를 적용합니다. 계정별 각 목록 최대 10,000개·문서 8MB, 최근 이력 500건·중복 요청 기록 256건 한도가 있습니다. 대규모 운영을 위한 관계형 확장·감사 로그 장기 보존은 별도입니다.
