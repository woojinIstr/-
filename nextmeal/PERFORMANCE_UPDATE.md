# 응답 지연 개선 v0.3.2

## 기존 v0.3 / v0.3.1에서 교체하는 순서

1. 기존 서버 실행 창에서 Ctrl+C를 눌러 종료한다.
2. 새 ZIP을 **새 폴더에** 압축 해제한다. 이전 폴더는 백업으로 보관한다.
3. 기존 backend/.env를 새 backend/.env로 복사한다. 기존 URL과 Publishable key를 유지한다. 로컬 모드라면 실제 *.db 파일도 같은 상대 위치로 복사한다.
4. START_WINDOWS.cmd를 실행한다. 새 인증 라이브러리를 처음 한 번 설치한다.
5. http://127.0.0.1:8000/?debug=performance 에서 기존 계정으로 로그인한다.
6. 화면 아래 ‘개발용 요청 성능’을 확인한다. 일반 주소에는 이 개발용 표가 나타나지 않는다.

**새 SQL은 없다. 이미 003까지 적용한 사용자는 SQL을 다시 실행하지 않는다.** 기존 데이터와 API 본문 형식을 유지한다. 새 프론트 빌드를 포함하므로 ZIP 그대로 실행할 때 Node.js는 필요 없다. GitHub에는 backend 변경을 B, 통합 프론트·실행 파일 변경을 D 브랜치에 공유한다.

## 이번 변경: 인증 요청 최적화

AUTH_VERIFICATION의 기본값은 auto다. 기존 .env에 이 줄이 없어도 자동 적용된다.

- ES256·RS256·EdDSA 토큰은 설정된 SUPABASE_URL의 공개키(JWKS)로 검증한다. 알고리즘은 서버의 허용 목록과 신뢰한 키의 알고리즘으로 제한한다. 서명·만료·발급 시각·발급처·대상·사용자 UUID·authenticated 역할을 매 요청 검증한다.
- 공개키만 5분 동안 보관한다. 토큰·사용자 정보·로그인 성공 결과를 캐시하지 않는다. 동시에 접속해도 공개키 조회는 한 번만 진행한다.
- 모르는 키 ID는 30초에 한 번까지만 공개키를 다시 조회한다. 확인되지 않은 키는 기존 Auth 서버로 검증한다. 공개키 조회가 실패하거나 HS256 프로젝트인 경우도 기존 사용자 확인을 유지한다. 검증하지 않은 토큰의 사용자 ID를 신뢰하지 않는다.
- 공개키는 항상 설정된 프로젝트에서 가져온다. 토큰에 들어 있는 외부 키 주소는 사용하지 않는다. 공개키 조회에 사용자 토큰을 전송하지 않는다.
- 공개키 조회에는 짧은 연결·응답 제한을 적용하고, 기존 HTTP 연결 풀을 재사용한다.
- 모든 DB 조회·저장은 기존 사용자 토큰을 그대로 전달하며 Supabase RLS와 revision 비교를 유지한다. DB가 토큰을 거부하면 앱도 거부한다.
- 서명 키 생성·교체, 프로젝트 지역 이동, DB 함수 변경은 자동 수행하지 않는다.

아래 횟수는 계정 데이터가 이미 존재하고 충돌·재전송이 없는 정상 경로 기준이다. 최초 데이터 가져오기, 공개키 갱신·실패·키 교체 시에는 추가 요청이 발생할 수 있다.

| 인증 경로 | 조회 | 미리보기 | 저장 |
|---|---:|---:|---:|
| v0.3.1 및 기존 Auth 서버 확인 | 2회 | 2회 | 3회 |
| v0.3.2, 공개키 캐시 사용 시 | 1회 | 1회 | 2회 |
| v0.3.2, 공개키를 처음 가져오는 요청 | 2회 | 2회 | 3회 |

**HS256이면 이번 공개키 최적화로 인증 요청이 줄어들지 않는다.** 먼저 표나 로그에서 실제 인증 방식을 확인한다. 키 변경은 별도의 검토와 작업이 필요하다.

공개키 검증은 JWT의 유효성을 확인하며, 매 요청 현재 사용자 계정 상태를 조회하지는 않는다. 현재 사용자 상태를 항상 재확인해야 하는 운영 정책이면 backend/.env에 AUTH_VERIFICATION=remote를 넣고 서버를 재시작한다. Supabase 서명 키 설정은 건드리지 않는다. 토큰은 원래 만료 전까지 유효할 수 있으므로 로그아웃·계정 상태 정책과 함께 운영해야 한다.

## 실제 시간 확인

개발용 주소: **http://127.0.0.1:8000/?debug=performance**

로그인 후 ‘새로고침’을 3~5번 누르고, 미리보기와 테스트용 수동 장보기 저장을 확인한다. 저장·구매 체크는 실제 데이터를 바꾸므로 본인 테스트 항목으로 진행한다. 화면 아래 표의 응답 수신·서버·인증·DB 시간을 비교한다.

| 항목 | 의미 |
|---|---|
| 응답 수신 | 브라우저에서 토큰 확인/갱신을 시작한 뒤 API 응답 JSON 처리까지의 시간. 원격 조작 도구의 시간과 화면 그리기는 제외 |
| 서버 | FastAPI의 Server-Timing total 값 |
| 인증 / DB 조회 / DB 저장 | 각 처리 구간의 서버 시간 |
| 외부 요청 | 해당 API가 Supabase로 보낸 요청 수 |
| jwks | 공개키로 토큰 검증 |
| remote-legacy | HS256이어서 기존 Auth 서버 확인 유지 |
| remote-forced | AUTH_VERIFICATION=remote 설정 |
| remote-fallback | 키 확인 불가 등으로 Auth 서버에 확인 |
| jwt-rejected | 토큰 검증 거절 |
| local-demo | Supabase를 쓰지 않는 로컬 시연 모드 |

표는 이 탭의 최근 20개 요청만 표시하며 다른 곳에 전송하거나 저장하지 않는다. 요청 경로·HTTP 상태·시간·횟수·인증 방식만 포함한다. 토큰·이메일·키·입력 데이터·응답 본문은 기록하지 않는다. 측정 표 오류가 저장 성공을 실패로 바꾸지 않도록 분리했다.

서버 실행 창의 nextmeal_timing에도 auth_method를 추가했다. 기존 total_ms, auth_ms, db_read_ms, db_write_ms, compute_ms, upstream_requests, request_id는 유지한다. auth_ms는 공개키 탐색·동시 요청 대기·로컬 서명 검증 또는 Auth 서버 확인을 포함하며, 중첩 통신 시간을 두 번 더하지 않는다. 응답 헤더에는 X-Auth-Verification을 추가했다.

## 실제 v0.3.1 기준값과 한계

사용자가 제공한 Windows·Supabase 로그 16건을 기준으로 계산했다. 원격 브라우저 조작 시간이 포함된 이전 관찰값과 구분한다.

| 작업 | 건수 | 평균 | 최소~최대 |
|---|---:|---:|---:|
| 조회 | 6 | 823.16ms | 378.50~1466.27ms |
| 미리보기 | 4 | 1324.62ms | 726.34~2577.48ms |
| 저장 | 6 | 1239.41ms | 673.81~1811.17ms |

이번 코드의 모의 Supabase·실제 서명 검증 시험에서는 공개키를 재사용할 때 요청 횟수가 줄어드는 것을 확인했다. **사용자의 새 실행본에서 몇 ms 빨라졌는지 또는 편차가 얼마나 줄었는지는 아직 측정하지 않았다.** 같은 환경에서 여러 번 비교해야 하며, 공개키 최초 조회 시간은 정상 재사용 요청과 구분한다. 현재 프로젝트 지역은 확인되지 않았으며 지역 이동도 진행하지 않았다.

## v0.3.1에서 유지한 개선

- Supabase HTTP 연결 풀 재사용(최대 20개, 유휴 10개, 유지 60초), 사용자별 Authorization 분리, 프록시 환경 설정 유지.
- compact=true 미리보기. 기존 기본 before/after 응답 호환.
- 재료 종류 추가·수동 장보기 추가·구매 체크 바로 저장.
- 저장 응답 유실 시 원래 request_id로 재확인하고 중복 저장 방지.
- 임시 SQLite·가상 이력 500개 기준 미리보기 응답 크기 비교는 backend에서 python tools/benchmark_preview.py로 재현 가능하다. 실제 Supabase 속도 시험은 아니다.
